# cairn-map：需求 → 架构 → 节点图

产出机读的 `.cairn/board.json`（节点 DAG）与人读的计划摘要。**本阶段不写业务代码。**

## 先确认

1. 读 `.cairn/board.json`，拿到 `goal`（没有就先 `/cairn init --goal "..."`）
2. 读项目约定：`AGENTS.md`、`README.md`、构建与测试命令
3. 读测试目录，确认验收能落在具体用例上

## ① survey：只读分析

- 模块划分与各自职责
- 模块之间的调用边界（谁调谁、传递什么）
- 现有测试覆盖了哪些行为
- 构建 / 测试 / lint 命令

把结论写进 `modules` 与节点 `consumes`/`provides`，不要写进聊天记录就丢掉。

## ② 架构

```jsonc
"modules": [
  { "name": "auth", "responsibility": "认证与会话", "dependsOn": ["db"] },
  { "name": "api",  "responsibility": "HTTP 入口",  "dependsOn": ["auth"] }
]
```

模块名一旦写入就是稳定标识：节点的 `module` 必须从中取。

## ③ 拆节点（决定成败的一步）

一个节点必须同时满足**四条硬标准**，不满足就再拆：

1. **可独立验收** —— 有自己的 `acceptance`，能映射到具体测试文件
2. **单会话可完成** —— 预计改动 ≤ 200 行
3. **边界清楚** —— `touches` 不与其它节点重叠
4. **接口可声明** —— `provides` / `consumes` 能写成签名

### 强制：把需求逐条落成可执行断言

**这是本阶段最容易偷懒、后果最重的一步。** 给定测试只覆盖需求的一部分；
需求里没写成测试的条款（如「未知 sku 返回 0」），不落成断言就**一定**会在实现里漏掉。

对每个节点做两件事：

1. **`acceptance` 逐条列举该节点的需求句子**，包括边界与例外。不许只写「能工作」。
2. **`probes` 声明规格探针文件**（如 `spec-probes/<module>.spec.mjs`），把给定测试**没覆盖**的条款落成断言。

必须扫到的边界类型（拿不准就都写上）：

| 类型 | 例子 |
|---|---|
| 未知键 / 原型链键 | `stock("toString")`、`stock("__proto__")`、`map.get("constructor")` |
| 空值 / 全空白 | `""`、`"   "`、`null`、`undefined` |
| 数值边界 | `0`、负数、小数、`NaN`、`Infinity` |
| 重复调用 | 同一 key 再调一次、取消后再取消 |
| 返回副本 | 改返回值后内部状态是否被污染 |
| 顺序不变量 | 事件 append 与状态变更的先后 |

`probes` 里的文件**必须同时写进 `touches`**，否则提交时会被边界门拒。
给定测试（`tests`）不许改，增补一律进 `probes`。

### 反例（验收会抓）

```text
✗ 只有 acceptance: ["能下单"]
✗ probes: [] 但需求写了「未知 sku 返回 0」
✓ acceptance: ["未知 sku 返回数字 0（含 toString/constructor/__proto__）", "库存不足抛错且库存不变"]
✓ probes: ["spec-probes/orders.spec.mjs"]
```

| 坏节点 | 为什么坏 | 怎么拆 |
|---|---|---|
| 「实现登录」 | 跨多模块、无法独立验收 | 拆成 token 生成 / token 校验 / 端点接线 / 前端回调 |
| 「重构 auth 目录」 | 没有验收判据 | 先定行为不变的验收（现有测试全绿），再按文件拆 |
| 「优化性能」 | 判据不可判定真伪 | 改成「P95 < 200ms 且基准测试可复现」 |

**`touches` 必须是具体文件或 `目录/`**，禁止 `src/**` 这类通配——边界门会形同虚设。

**`tests` 不许留空**：留空意味着该节点没有验收载体，验收会直接判 fail。

**`probes` 不许为空**（当 config 含 `{probes}` 级别时）：留空直接判 fail。

## ④ 写入

调用 `cairn_map_write`，传 `modules` 与 `nodes`（每个节点含 `probes`）。契约不合法会被拒（模块未声明、依赖指向不存在节点、`touches` 为空等）。

## ⑤ 停在闸门

写完向用户报告：

```text
地图就绪：<n> 模块 / <m> 节点
可立即执行：n01, n02（无依赖）
需等待：n03（依赖 n01, n02）
确认执行：/cairn execute    仅看计划：/cairn status
```

**不要**在确认前开始改代码。

## 重规划模式

带 `--replan <nodeId>` 时：

1. 只重规划该节点及其下游（`dependents`）
2. 已 `done` 的节点与全部证据保留，**不许重置**
3. 只改需要改的节点，其余原样传回 `cairn_map_write`

## 禁止

- 不改业务代码（本阶段只读）
- 不替用户决定技术选型；有真实取舍就列 2–3 个选项交人决定
- 不为了让图「看起来完整」而编造节点；一个节点都没有就说明需求还没拆开
