# Cairn 核心架构提取

源码：`Cairn`。实现细节见 [`cairn-core-dispatch.md`](cairn-core-dispatch.md)；
本文只提取**可迁移的架构**，去掉规模产物（容器、租约、多 dispatcher）。

## 1. 一句话

> 给定 **origin** 和 **goal**，在未知状态空间里做**有向搜索**；搜索状态放在一块**公共黑板**上，
> 无固定角色的代理通过**读写黑板**协作（stigmergy），**调度由确定性代码完成**。

渗透测试只是第一个验证域。同理适用：漏洞研究、数学证明、CTF、**以及开发任务**。

## 2. 三原语

| 原语 | 定义 | 关键约束 |
|---|---|---|
| **Fact** | 已确认的客观发现 | 必须是事实，不是主张 |
| **Intent** | 声明的探索方向，尚未执行 | `from` 指向派生自哪些 Fact |
| **Hint** | 人类判断，随时注入 | 下一轮读取时被吸收 |

图从 `origin`（起点 Fact）长向 `goal`（终点 Fact）。每条新 Fact 是一块垫脚石，每条 Intent 是迈向未知的一步。

## 3. 六个可迁移的设计原则

### P1 · 黑板是唯一协调面（Stigmergy）

代理之间**不直接通信**、无信息孤岛。所有协调通过共享黑板发生：一个代理写下的 Fact，成为另一个代理的输入。

> 为什么有效：代理无需知道彼此存在，也就无需为「谁负责什么」付协调成本。搜索状态的外部化让任意数量的代理都能接力。

### P2 · 无固定角色，任务从图状态现生成

代理不是「测试工程师」「代码审查员」。任务在运行期由图当前形态决定：

| 任务 | 触发条件（图状态） | 产出 |
|---|---|---|
| `bootstrap` | 初始态（只有 origin + goal） | 直接尝试整体解决 |
| `reason` | 出现**新态势** | 判断是否完成 / 提出新 Intent / 不作声 |
| `explore` | 存在未认领 Intent | 执行一条 Intent，产出一条 Fact |

> 为什么有效：预定义角色是**对未知路径的猜测**。图知道得多，让它决定下一步。这是「无 workflow」的真正含义。

### P3 · 调度是确定性代码，不是 prompt

Dispatcher 是普通程序：拉图 → 判断状态 → 选任务 → 起进程 → 校验输出 → 写回。模型只在**单个任务内部**活动。

> 为什么有效：把「谁该做什么」交给模型，等于每轮重新猜一次控制流，且无法审计。控制流归代码，探索归模型。

### P4 · 结构化输出契约 + 强制校验

每个任务只返回一个 JSON 对象，字段固定：

```json
{"accepted": true, "data": { ... }}
```

校验不过 = 任务作废，**绝不写图**。`accepted:false` 视为拒绝，同样不写图。

> 为什么有效：非结构化输出无法被程序消费，一次格式漂移就污染整条链路。契约让「失败」成为一等公民。

### P5 · 代理上下文隔离

每个 worker 是一个独立进程，只收到「渲染好的任务 prompt + 图快照」。它看不到完整对话历史，也看不到别的 worker。

> 为什么有效：这是搜索不发散的根本原因。上下文越长，探索越倾向自我重复；隔离让每次探索从同一份**干净的黑板状态**出发。

### P6 · 双阶段收尾（单阶段失败不等于零产出）

主阶段超时或输出非法 → 用**同一个 session** 再跑一次收尾 prompt，要求「不继续推进，只总结截至目前已确认的事实」。

> 为什么有效：探索的价值常在于「发现了什么」，而不是「完成了什么」。收尾把沉没成本转成 Fact。

## 4. 核心洞察：为什么这套架构比单发 agent 强

| 单发 agent | 黑板搜索 |
|---|---|
| 上下文线性增长，越往后越易重复/发散 | 每轮从同一份黑板快照出发 |
| 失败 = 零产出（对话丢弃） | 失败也可能产出 Fact |
| 只有一条路径 | 多条 Intent 并行探索 |
| 「做完了」由模型自述 | 「做完了」由 reason 读图判断 |
| 无法中途干预 | Hint 随时注入 |

## 5. 什么不该迁移（规模产物，不是架构）

| Cairn 原语 | 存在理由 | 单机版处理 |
|---|---|---|
| Server (HTTP + DB) | 跨进程共享图 | 换成本地文件 |
| claim / heartbeat / lease | 多 dispatcher + 多容器竞争 | 砍掉（单进程无竞争） |
| Docker per-project 容器 | 执行环境隔离 + 工具链 | 砍掉（worker 直接在本机子进程跑） |
| 多 worker 选择算法 | 并发配额与优先级 | 砍掉（单 worker） |
| 双阶段 conclude 的 session 复用 | 进程内状态延续 | 可保留（pi 支持 session id），第一版先砍 |

**判断标准**：它解决的是「多方同时改图」还是「如何搜索」？前者砍，后者留。

## 6. 迁移到 pi 的架构映射

| Cairn | pi 原生对应物 |
|---|---|
| Server（图真相源） | 扩展内存态 + 本地 JSON 文件 |
| Dispatcher（调度器） | 扩展内的确定性循环 |
| Worker（隔离代理进程） | spawn `pi --mode json -p` 子进程 |
| `contracts.py` 校验 | TypeBox schema / 手写校验 |
| `prompts/*.md` 模板 | 包内 profile 的 Markdown 模板 |
| Hint 注入 | `/cairn hint` 命令 |
| 图渲染 | `/cairn status`（TUI 或纯文本） |

## 7. 通用化：架构 vs 领域

Cairn 的**架构**是通用的；它的**领域知识**在 prompt 与校验规则里。所以正确的包结构是：

```
通用引擎（黑板 + 调度 + 契约 + 证据门）
        ↓ 由 profile 注入
领域档案（prompt 措辞 + 事实类型 + 验证方式）
```

- `coding` 档案：origin=当前代码库，goal=实现/修复/测试绿，验证方式=跑命令看退出码
- `research` 档案：origin=已知信息，goal=待answering的问题，验证方式=引用来源
- `generic` 档案：不声明验证方式，Fact 靠 worker 判断

**引擎一行不为某个领域改变**，这是架构是否真的通用的判据。

## 8. 我在 Cairn 之上必须补的一条：证据门

Cairn 假定 Fact 是「已确认的」。**这个假定在开发任务上不成立**——代理写下「已修复」，不代表真的修复。

Cairn 的 reason 读图判断完成，但执行者与判断者可以是同一个模型的两次调用，容易自我确认。

补充设计（这是 `cairn-pi` 相对 Cairn 的核心增量）：

1. **Fact 分三态**：`candidate`（代理主张）→ `confirmed`（证据通过）| `refuted`（证据否证）
2. **只有 `confirmed` 的 Fact 能作为 `intent.from`**——未验证的主张不生长图
3. **新增第四个任务 `verify`**：拿 `candidate` Fact，用**全新上下文**独立复核，只返回通过/否证 + 证据
4. **证据必须可复验**：优先机器可验（命令 + 退出码 + 输出片段），其次人工可核（文件行号 + 引用）

> 为什么有效：把「我做了」和「它成立」拆成两次独立判断，是提高开发效果最便宜的一刀。
