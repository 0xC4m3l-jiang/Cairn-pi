## 1. 需求与验收

**要解决什么**：设计与决策散落在对话里，没有可据以开工的文档；没有可跑的验证命令。

**做完之后，用户能做什么**：
- 打开 `README.md` 知道这包干什么、怎么装、怎么用
- 打开 `DESIGN.md` 看到全部锁定决策、数据模型字段字典、状态机门禁、切片规则、失效条件
- 打开 `DEVELOPMENT.md` 按 M0–M7 里程碑直接开工，知道每个模块的导出签名
- 跑 `npm run verify` 一条命令验证代码是否仍然成立

**验收判据**：

1. `README.md` / `DESIGN.md` / `DEVELOPMENT.md` 三份文档存在且互相链接不悬空
2. `package.json` 符合 pi 包规范：`keywords` 含 `pi-package`、宿主包在 `peerDependencies` 而非 `dependencies`、声明 `pi.extensions`/`pi.skills`
3. `npm run verify` 通过（typecheck + 测试）
4. `.pi/devloop.md` 的 `verify_cmd` 与 `AGENTS.md` 的一键验证命令一致，且实际跑得通
5. `DESIGN.md` 含字段字典、状态机门禁矩阵、非目标、失效条件

**不做什么**：
- 不写 `lib/board.ts` / `gates.ts` / `verify.ts` / `coverage.ts`（M1–M4）
- 不写 `extensions/` 与 `skills/`（M5–M7）
- 不做并行执行

## 2. 设计逻辑

**决策树**：

```text
文档体系与包骨架
├── 文档怎么分（三份互不重复）
│   ├── README      门面：是什么/怎么装/怎么用
│   ├── DESIGN      为什么：决策/模型/门禁/失效条件
│   └── DEVELOPMENT 怎么做：职责/契约/里程碑/测试
└── 验证入口怎么定
    └── npm run verify = tsc --noEmit + vitest run
```

**已确认的决策**：

| # | 问题 | 决定 | 理由 | 落地位置 |
| --- | --- | --- | --- | --- |
| ① | 文档分几份 | README / DESIGN / DEVELOPMENT 三份 | 门面、设计、开发各自读者不同，混写会互相污染 | 三个根文件 |
| ② | 验证命令 | `npm run verify` | 不引入 Makefile；typecheck + 测试一个命令覆盖 | `package.json`、`.pi/devloop.md`、`AGENTS.md` |
| ③ | M0 是否写代码 | 写 `contracts.ts` + 测试 | 验证命令必须真实可跑，否则适配面是空话 | `lib/contracts.ts`、`tests/` |
| ④ | Cairn 文档放哪 | `docs/` 下保留两份提取 | 属参考资料，不是本项目的规范层 | `docs/` |
| ⑤ | 宿主包依赖 | 只写 `peerDependencies` | 写 `dependencies` 会装出重复实例，类与注册表分裂 | `package.json` |

**仍未定**：无（阻塞项为零）。

**接缝与接口**：`lib/contracts.ts` 是本轮唯一导出契约。其余模块（M1–M4）全部依赖它，
所以先定型 `CairnBoard` / `CairnConfig` / `CairnNode` / `Finding` / `EvidenceLevel`。

**数据流**：`board.json`（磁盘）→ `parseBoard`（校验）→ `CairnBoard`（内存）→ 后续模块。
失败路径：结构非法 → 抛 `ContractError`，带「哪个字段 / 为什么」。

**本轮的教训（记入方法论，不只记入本次返工）**：

1. 声称「零命中」「已完成」「已验证」前必须**跑命令**，不靠印象。R6 正是凭印象断言导致的。
2. 同一个概念在两处出现时，改一处就要 grep 全局，否则留的是**永远填不上的占位符**。
3. 文档里写「本项目自建 / 已实现」时，必须能指出文件；指不出就写「人工核」。
4. 模板文件里不要混入日志正文；模板与实例分开放。
