## 1. 需求与验收

**要解决什么**：项目名与目录名是 `Carin-pi` / `pi-cairn`，用户要求统一为 `cairn-pi`；同时要一份对比证据，判断本包是否真的提升开发效果。

**做完之后，用户能做什么**：
- 目录叫 `cairn-pi`，包名 `cairn-pi`，文档零残留旧名
- 跑 `demo/run-baseline.sh` / `demo/run-cairn.sh` 复现对比
- 读 `demo/RESULTS.md` 知道什么时候值得用、什么时候不值得

**验收判据**：

1. `grep -rn "pi-cairn\|Carin-pi"` 在仓库内零命中
2. `npm run verify` 通过（77 例）
3. 文档承诺的 `--plan` / `--replan` / `--verify-only` / `cairn_board_read` 过滤全部可用
4. 两组实验都有可复核的产物与指标
5. 旧目录名不再作为实体存在

**不做什么**：不改设计（D1–D7 不变）；不做并行执行；不优化实验里暴露的收尾空转。

---

## 2. 设计逻辑

**改名策略**：先 `mv` 目录，再建符号链接 `Carin-pi -> cairn-pi` 保住当前会话的 cwd；
全仓 `perl -pi -e 's/pi-cairn/cairn-pi/g; s/Carin-pi/cairn-pi/g'`；
最后在收尾时删除符号链接。

**实验设计**（详见 `demo/README.md`）：
两条路线拿**完全相同**的需求文本与**预先写好、双方都不许改**的验收测试；
指标在开跑前固定；给出失效判据，避免事后挑指标。

**取舍**：

| 取舍 | 决定 | 理由 |
|---|---|---|
| B 组是否给流程提示 | 给 | 工具的实际用法就是它的干预；不给等于测了个没配置的包。已在结果里标注这一不对称 |
| 公平性 | 两组同起点、同测试、同判据 | —— |
| 需求规模 | 单文件三需求 | 有意选小的：若小任务都赢不了，说明价值只在结构性场景 |

## 7. 遗留与未决

| # | 遗留 | 影响 | 去向 |
|---|---|---|---|
| 1 | B 组内层 agent 在最后一步空转约 4 分钟，需父会话补收尾 | 长任务可能挂住 | 加「收尾超时 + 自动收束」：节点全 done 时自动跑 integrate |
| 2 | 实验每组只跑 1 次 | 结论受单次波动影响 | 需要时说，不声称统计显著 |
| 3 | `--verify-only` / `--replan` / `board_read` 过滤无用例 | 回归风险 | 下一轮补 |
| 4 | 并行执行未做 | 大需求线性耗时 | v2 |
| 5 | 旧目录名 `Carin-pi` 的符号链接 | 只为本会话 cwd 存活 | 收尾时删除 |
